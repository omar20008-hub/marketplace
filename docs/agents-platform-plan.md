# خطة إضافة منصة وكلاء LangGraph (الوكيل الأول: Ads Manager)

الحالة: مسودة للمراجعة. لا كود بعد. مصدر القرارات: ملف «ملخص قرارات بناء المنصة الوكيلية» (نوفمبر 2026) وإجابات المالك:

| القرار | الاختيار |
|---|---|
| من يبني الوكلاء | نحن الآن؛ يُفتح للمستخدمين لاحقًا (لذلك تُصمَّم الحدود كأن الكود غير موثوق) |
| الوكيل الأول | Ads Manager |
| المستودع | نفسه، مجلد `agents/` |
| النموذج | Gemini عبر LiteLLM |
| مكان التشغيل | Railway، خدمة جديدة بجانب المنصة |

## 1. ما تملكه المنصة اليوم (يغيّر الخطة)

المنصة تنفّذ جزءًا كبيرًا من منطق الإعلانات في الكود، وليس في n8n:

- `POST /api/ads/campaigns` ينشئ الحملة **متوقفة (PAUSED)** في Meta، بعد التحقق عبر `src/lib/ads/validate.ts`، ويعيد مراجعة (`review`) تتضمن سقف الصرف.
- `POST /api/ads/campaigns/{id}/activate` يشغّلها، ويشترط `confirmedMaxTotalCents` مطابقًا للسقف المحسوب لحظتها. يحجز الصف بمقارنة وتبديل (PAUSED → ACTIVE) فلا يُشغَّل مرتين.
- الإنشاء يحجز الصف (DRAFT → CREATING) ويحفظ كل معرّف Meta فور وصوله. هذه هي الـ idempotency التي يطلبها الملف.
- المصادقة بمفتاح التثبيت `kb_…` (`installationForKey`) مع تحديد معدل.
- `ProductKind` فيه `AGENT` أصلًا (يُستخدم الآن لمنتجات n8n ذات الطابع الوكيلي)، و`Run` يسجّل التشغيل والتكلفة، وقنوات واتساب وتيليغرام والمحادثة جاهزة، ونقطة `/api/n8n/thread-message` تكتب في خيط المحادثة.

**الانحراف المقترح عن الملف:** الملف يقول «حملات Meta دائمًا عبر n8n». هنا يتحدث الوكيل مع **نقاط المنصة مباشرة**، لأنها تنفّذ الحرفية والـ idempotency وبوابة المال أصلًا، وn8n سيكون طبقة زائدة بلا فائدة. يبقى مبدأ الملف سليمًا: الوكيل يملك كل شيء قبل «موافق»، والمنصة (التنفيذ الحتمي) بعده. وn8n يُستخدم حين يكون هناك workflow قائم فعلًا.

## 2. البنية

```
المستخدم (محادثة / واتساب / تيليغرام)
        │
   Orchestrator (n8n)  ──أداة "ads_manager"──►  المنصة (Next.js)
                                                    │  POST /api/agents/{slug}/runs   (داخلي، موقّع)
                                                    ▼
                                    خدمة الوكلاء (Python · FastAPI · LangGraph)   ← Railway
                                       │  LiteLLM → Gemini          │  PostgresSaver (قاعدة وكلاء منفصلة)
                                       ▼                            ▼
                         أدوات = استدعاءات HTTP لواجهة المنصة    Langfuse (تتبّع)
                         (/api/ads/*, /api/files, الذاكرة)
```

- **الخدمة لا تحمل أسرار المستخدمين.** لا ترى رمز Facebook. تنادي المنصة بمفتاح التثبيت، والمنصة تحتفظ بالاتصال وتفكّ تشفيره. هذا نفس نموذج Drive عندنا ويجعل فتح الوكلاء لمستخدمين آخرين أقل خطرًا لاحقًا.
- **الهوية من المنصة فقط:** `tenant_id` و`user_id` و`thread_id` تبنيها المنصة من الجلسة الموثّقة وتوقّع الطلب (HMAC بسر مشترك + طابع زمني). الخدمة ترفض أي طلب بلا توقيع صالح. لا شيء من المتصفح أو من النموذج.
- **`thread_id` للـ checkpointer** = `agent:{installationId}:{runId}`، يبنيه الخادم، ولا يُقبل من الخارج.
- **قاعدة منفصلة** لـ PostgresSaver (خدمة Postgres ثانية، أو قاعدة ثانية على النسخة الحالية). لا تدخل Prisma ولا migrations المنصة.

## 3. العقد بين المنصة والخدمة

الطلب (المنصة ← الخدمة):

```
POST /v1/runs
X-Signature: hmac(timestamp + body)    X-Timestamp
Idempotency-Key: {runId}
{ "agent": "ads-manager", "tenantId": "...", "userId": "...", "installationId": "...",
  "threadId": "...", "input": { "message": "..." } }
```

الرد (موحّد): `{ "status": "done" | "needs_input" | "awaiting_approval" | "error", "data": {...}, "error": null }`

- `needs_input`: يحمل السؤال الناقص (مثل ميزانية أو جمهور).
- `awaiting_approval`: يحمل ملخص المراجعة (السقف، المدة، الجمهور) و`approvalId`.
- الاستئناف: `POST /v1/runs/{runId}/resume` بالموافقة أو الرفض أو التعديل.

الاستدعاء غير متزامن للمهام الطويلة: ترجع الخدمة فورًا بـ `runId`، وتكتب النتيجة في الخيط عبر منصة المنصة (نفس آلية الفيديو)، لأن اتصال المحادثة يُقطع عند نحو 60 ثانية.

## 4. وكيل Ads Manager (graph عمودي)

العقد، وكل عبور بينها بمخرجات منظّمة (JSON schema) تُتحقق قبل التفرّع:

1. **collect**: يستخلص المتطلبات من المحادثة (الهدف، الميزانية اليومية، البلدان، العمر، المنصات، النص، الرابط، الصورة، التواريخ). إن نقص شيء → `needs_input` بسؤال واحد واضح.
2. **validate**: يستدعي منطق `validateAdCampaign` نفسه. **نضيف نقطة تحقق دون أثر** `POST /api/ads/validate` (أو `dryRun: true`) كي لا تُكرَّر القواعد في Python.
3. **creative_check**: يتحقق من أن الصورة JPEG/PNG وأن الرابط يفتح، ويقترح تحسين النص (Gemini).
4. **create_paused**: ينشئ الحملة المتوقفة عبر `/api/ads/campaigns` بمفتاح `Idempotency-Key` ثابت للتشغيل. لا مال يتحرك.
5. **approval**: `interrupt()` بالمراجعة (السقف الأقصى للصرف). الموافقة تصل عبر القناة نفسها (محادثة / واتساب / تيليغرام) وتطابق السقف **حرفيًا**، لا «نعم» عامة.
6. **activate**: يستدعي `/activate` بـ `confirmedMaxTotalCents`. المنصة تعيد الفحص وترفض إن تغيّر شيء.
7. **report**: ملخص النتيجة ومعرّفات Ads Manager.

قواعد ثابتة: لا فرع على نص حر؛ لا تفعيل بلا `interrupt` مؤكَّد؛ أي رفض من المنصة يُعرض للمستخدم بكلامه ولا يُعاد تلقائيًا.

لاحقًا (بعد الاستقرار): تقارير الأداء والتحسين الاستباقي (Schedule من n8n أو المنصة يستدعي الوكيل)، إيقاف الحملات، تعديل الميزانية بموافقة.

## 5. تغييرات في المنصة (Next.js)

- **`Product.kind = AGENT` موجود.** نضيف حقل/نوع تشغيل (`runtime`: `n8n` | `langgraph`) على `Product` وmigration إضافية فقط. منتج `langgraph` له `agentSlug` بدل قالب n8n.
- **مسار التشغيل:** في `executeRun()` فرع جديد قبل الـ dispatcher: إن كان `runtime = langgraph` يمر عبر عميل جديد `src/server/agents/client.ts` (توقيع، مهلة، معالجة `awaiting_approval`). كل فحوص الخطة والحصة والجاهزية تبقى كما هي (`executeRun` تفحص قبل أي استدعاء).
- **التثبيت:** يُنشئ `Installation` ومفتاح `kb_` كالمعتاد، ولا ينسخ workflow.
- **الموافقات:** جدول `AgentApproval` (runId، الملخص، السقف، الحالة، انتهاء الصلاحية) وواجهة تعرضها وتقبل الموافقة، ومسار القنوات ليستقبل الرد ويستأنف. يتبع نمط `confirmations` الموجود.
- **الـ Orchestrator:** أداة `ads_manager` تظهر في الكتالوج من التثبيت، فلا حاجة لتغيير بنيته (كل رسالة تمر عبره كما طلبت).
- **التكلفة:** الاستئناف بعد الموافقة لا يُحتسب تشغيلًا ثانيًا (`charged` مرة واحدة لكل `runId`).

## 6. المجلد والنشر

```
agents/
  CLAUDE.md            قواعد البنية والعقد (من مسودة الملف)
  pyproject.toml       إصدارات مثبّتة (langgraph, langchain-core, litellm, fastapi, psycopg, langfuse)
  Dockerfile
  src/agent_platform/
    api.py             FastAPI: /v1/runs, /resume, /health
    security.py        التحقق من HMAC والمهلة
    gateway.py         LiteLLM (النموذج من متغير بيئة)
    platform_client.py استدعاءات المنصة (الأدوات)
    graphs/ads_manager.py
    schemas.py         pydantic للمدخلات والمخرجات
  tests/               عقد + graph بنموذج وهمي + أمان
```

- **Railway:** خدمة `agents` من المستودع (Root Directory = `agents`، Dockerfile)، وPostgres ثانٍ لها، وdomain **داخلي** فقط (`agents.railway.internal`) لأن المنصة وحدها تناديها. لا نفتحها للإنترنت.
- **متغيرات:** `AGENTS_SIGNING_SECRET`، `PLATFORM_URL` (داخلي أو `PUBLIC_URL`)، `GEMINI_API_KEY`، `AGENTS_DATABASE_URL`، مفاتيح Langfuse. تُضبط في Railway لا في المستودع (قاعدة المشروع).
- **البيئات:** نبني على `worthy-bravery` (التطوير)، وننقل مع الانتقال للمنصة الجديدة.
- **CI:** مهمة منفصلة لـ `agents/` (ruff، mypy أو pyright، pytest)، لا تعطّل مهام Node.

## 7. الأمان والعزل (مهم لأن الوكلاء ستُفتح لمستخدمين)

- لا أسرار مستخدمين في الخدمة ولا في حالة الـ graph. الأدوات تمر بالمنصة.
- كل أداة تأخذ هوية المستخدم من سياق التشغيل (مُحقن)، **لا** من معاملات يكتبها النموذج.
- الحالة المخزّنة (checkpoints) تحمل معرّفات ونصوصًا فقط؛ لا مفاتيح ولا رموز.
- تحديد معدل وسقف تكلفة لكل تشغيل (عدد استدعاءات النموذج والأدوات) وحدّ زمني، لمنع الحلقات.
- ما يلزم قبل فتح الوكلاء لغير فريقنا: تشغيل كود الغير في صندوق معزول، وهذا خارج هذه الخطة.
- Langfuse Cloud خارج السعودية: لا نرسل له نصوصًا فيها بيانات عملاء حساسة؛ نُخفي الحقول أو نؤجل التتبع للنص الكامل.

## 8. الاختبارات

- **عقد المنصة ↔ الخدمة:** التوقيع، الطابع الزمني القديم، الهوية المفقودة، idempotency (نفس `runId` لا ينفّذ مرتين).
- **الـ graph بنموذج وهمي:** كل مسار (ناقص مدخلات، رفض، موافقة، رفض من المنصة، تغيّر السقف بين المراجعة والتفعيل).
- **اختبار حاسم:** لا يمكن الوصول إلى `activate` دون `interrupt` مؤكَّد (يُثبت ببنية الـ graph، لا بالنص).
- **اختبارات المنصة (Vitest):** فرع `langgraph` في `executeRun`، الاستئناف دون احتساب مزدوج، منع تشغيل تثبيت مستخدم آخر.
- **evals عربية:** مجموعة صغيرة (20–30 طلب إعلان بالعربية والخليجية) لقياس استخلاص المتطلبات قبل أي تبديل نموذج.

## 10. ما يجب حسمه قبل البدء

1. **ترخيص n8n** للاستخدام التجاري داخل منصة مستضافة (قائم، ويزداد مع التوسع).
2. **حساب الإعلانات:** نختبر على حساب Meta Ads تجريبي (Sandbox) لا على حساب عميل حقيقي. هل لدينا واحد؟
3. **الواجهة:** هل شاشة الموافقة تكفي في المحادثة وواتساب، أم نحتاج صفحة مراجعة مستقلة؟ (الإنشاء المتوقف يسمح بالاثنين.)
4. **من أين تُدفع تكلفة النموذج:** من حصة الخطة الحالية أم رصيد مستقل للوكلاء؟
5. **مسار الانتقال:** هل نبني على `worthy-bravery` أم ننتظر الانتقال لمشروع الإنتاج الجديد؟

## 11. ما أُجِّل عمدًا

Deep Agents (الوكيل الأفقي)، Composio، خدمة LiteLLM مستقلة، Langfuse ذاتي الاستضافة، النماذج المفتوحة، تشغيل كود المستخدمين. كلها تُضاف بعد استقرار نمط الوكيل الأول.
